# Дело — кредитный кабинет предпринимателя

Независимый MVP для хакатона: React 18 / TypeScript / Vite / Tailwind / shadcn-style Radix UI, Django 5.2 / DRF / PostgreSQL 16. Продукты, организации, ставки, проверки и кредитные решения синтетические. Реальных банковских интеграций и выдачи денег нет.

## Запуск

Нужен Docker Desktop с работающим Linux engine и Docker Compose v2.

```sh
docker compose up --build -d
```

Первый запуск скачивает образы и зависимости, применяет миграции и создаёт демо-данные. Адреса:

- Приложение: http://localhost:8080
- Swagger: http://localhost:8080/api/docs/
- OpenAPI: http://localhost:8080/api/schema/
- Проверка backend + БД: http://localhost:8080/health/

Локальные значения по умолчанию находятся в compose.yaml. Для собственных секретов скопируйте `.env.example` в `.env` и замените значения. Никаких регистраций, SMS или платных API не требуется.

| Логин | Компания / сценарий |
|---|---|
| demo_a | Северный свет — автоматическое одобрение |
| demo_b | Новая линия — встречное предложение |
| demo_c | Точка роста — ручное рассмотрение |
| demo_d | Контур — отказ из-за просрочки |
| bank | Сотрудник банка |

Пароль по умолчанию: `Demo-Credit-2026!`, либо значение `DEMO_PASSWORD` из `.env`. Это открытые тестовые учётные записи только для изолированной локальной демонстрации. HTTP-порт привязан к loopback; БД и backend не публикуются наружу.

```sh
docker compose ps
docker compose logs backend
docker compose exec backend python manage.py seed_demo --reset
```

`--reset` удаляет заявки, историю и результаты только четырёх демо-компаний и создаёт их заново. Файлы на диске не очищает. Без флага команда не дублирует заявки. При старте seed обновляет пароли демо-аккаунтов значением DEMO_PASSWORD.

## Проверка для жюри

1. Войти как `demo_a`. Открыть готовое предложение: 1 000 000 ₽, ставка 19,50%, 24 месяца. Изучить оценку, две проверки и историю. Принять предложение с подтверждением — статус «Завершена».
2. Выйти, войти как `demo_b`: на запрос 3 млн ₽ сформировано предложение 1,8 млн ₽, основанное на 30% выручки. Принять либо отклонить.
3. Войти как `demo_c`, открыть заявку «На рассмотрении». В отдельной сессии либо после выхода войти как `bank`. Найти компанию через поиск и статус. Изучить финансы, ФНС/БКИ и факторы оценки. Запросить дополнительные сведения с обоснованием.
4. Вернуться в `demo_c`: дополнить заявку и/или загрузить синтетический PDF до 5 МБ во вкладке документов. Снова отправить. В `bank` одобрить сумму в пределах запроса и ограничений продукта. Клиент увидит предложение при обновлении (автообновление карточки каждые 10 секунд).
5. Войти как `demo_d`: отказ с объяснением просрочки >60 дней. Изучить стоп-фактор во вкладке оценок.
6. В `demo_a` выбрать другой продукт, пройти мастер, сохранить черновик. Вернуться через «Мои заявки», отредактировать и отправить. Финансовые показатели определяют новое решение.
7. Проверить защиту: адрес чужой заявки возвращает 404; клиент не может вызвать ручное решение, сотрудник — принять клиентское предложение. Повтор принятия не создаёт второй переход.

## Проверки

```sh
docker compose exec backend pytest -c pytest.ini
docker compose exec backend python manage.py makemigrations --check --dry-run
docker compose exec backend python manage.py spectacular --file /tmp/openapi.yaml --validate
cd frontend
npm ci
npm run build
npm test
```

CI содержит PostgreSQL 16, тесты конкурирующего принятия и Compose smoke test. Наличие workflow не означает, что удалённый CI уже запускался. Фактические локальные результаты и ограничения приведены в [docs/verification.md](docs/verification.md).

## Разработка без Docker

Python 3.12+, Node 22+ и локальный PostgreSQL 16+:

```sh
pip install -r backend/requirements.lock.txt
# Установить DJANGO_SECRET_KEY, POSTGRES_HOST, POSTGRES_PORT,
# POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, DEMO_PASSWORD
python backend/manage.py migrate
python backend/manage.py seed_demo
python backend/manage.py runserver 127.0.0.1:8000
```

Во втором терминале: `cd frontend`, `npm ci`, `npm run dev`. Vite проксирует `/api` на порт 8000. SQLite допускается только для вспомогательных проверок через `SQLITE_TEST=1`; он не заменяет PostgreSQL и проверку блокировок.

В Postman сначала выполните CSRF, затем Login и снова CSRF: Django меняет токен при входе. Cookie jar должен быть включён. Для банковских запросов войдите как bank с тем же паролем.

Синхронные проверки выполняются в одной транзакции, промежуточные статусы появляются в истории после завершения. Не реализованы фоновые воркеры, реальные внешние проверки, антивирус, выдача денег, ЭП, MFA, production monitoring и юридические кредитные договоры. Результаты всех проверок собственной компании доступны клиенту в демо. Рабочий интерфейс банка использует тот же login с ролью is_staff, проверяемой сервером. Все денежные значения хранятся как Decimal; на клиенте Number используется только для предварительного калькулятора.

Для внешнего production-развёртывания требуется отдельная работа: HTTPS, собственные секреты, выключение demo seed, ограничение служебных аккаунтов, проверка зависимостей, резервирование и аудит безопасности. Текущая сборка предназначена для localhost.

Начальная версия зафиксирована тегом `hackathon-v1`, версия после сверки оригинального PDF — `hackathon-v2`. Получить SHA: `git rev-parse hackathon-v2`. Удалённый репозиторий и публикация не создавались; обязательный по PDF пункт GitHub ещё не выполнен.
